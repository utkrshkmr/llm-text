# Performance Engineering on One GPU {#ch:perf}

A distributed training job is a single-GPU program replicated thousands of times, with communication
added. Every inefficiency inside one device multiplies across the cluster: a step that leaves half
of each GPU idle wastes half the cluster, however clever the parallelism. This chapter is about
making a single device do as much useful work as possible, and about the measurements you need
before you change anything.

The tools come first: honest timers, the Nsight Systems profiler with NVTX annotations, the PyTorch
memory snapshot, and saved-tensor hooks that show exactly what autograd keeps for the backward pass.
With those in hand we take apart a training step: where the time goes, where the memory goes, what
mixed precision and `torch.compile` change, and how activation checkpointing trades FLOPs for bytes.
The chapter ends with the largest single optimisation for long-context training, a FlashAttention-2
kernel in Triton with *both* the forward and the backward pass, wired into autograd. It builds
directly on the derivation in [@sec:attention:flash] and on the forward-only kernel of
[@sec:triton:flash].

for a fast training step.](figures/ch17_perf_engineering-1.svg){#fig:perf:roadmap}

## A performance workbench {#sec:perf:workbench}

Performance work is experimental science, and the first deliverable is a laboratory in which
experiments are cheap, repeatable and recorded. Concretely, that means four things.

##### A pinned, recorded environment.

Driver, CUDA runtime, PyTorch, Triton and NCCL versions all change kernel selection and therefore
timings; a PyTorch upgrade can change which attention backend runs, and a Triton upgrade can change
the language itself (recent Triton releases removed the block-pointer API in favour of tensor
descriptors, see [@sec:perf:fa2:blockptr]). Use a lock file (`uv.lock` or
`requirements.txt` with exact versions) and record the environment next to every result.
`code/projects/p2_systems/env_check.py` prints versions, GPU models, SM counts, the interconnect
topology (`nvidia-smi topo -m`), whether `nsys`/`ncu` are installed, and a one-second matmul sanity
check against the published peak:

``` bash
$ python projects/p2_systems/env_check.py --json > results/env.json
$ python projects/p2_systems/env_check.py
torch: 2.x.y+cu12z   cuda: 12.z   triton: 3.y   nccl: 2.y.z
gpu[0]: {'name': 'NVIDIA H100 80GB HBM3', 'mem_GiB': 79.1, 'sms': 132,
         'cc': '9.0'}
matmul_check: {'bf16_TFLOPs': ..., 'fraction_of_peak': ...}
nsys: /usr/local/bin/nsys   ncu: /usr/local/bin/ncu
```

##### Benchmarks as programs with flags.

Every variation you will want to compare (model size, context length, dtype, compiled or not, which
attention, which checkpointing policy) should be a command-line flag of one script, not a copy of
it. Lab 16's `bench.py` follows this pattern with four sub-commands (`model`, `attention`, `saved`,
`ckpt`).

##### Sweeps that log failures.

Out-of-memory errors are results, not exceptions to swallow. `projects/p2_systems/sweep.py` runs a
command over a JSON grid, records one JSON line per run (including `"status": "oom"`), stores the
git revision, and resumes after an interruption.

##### Tables generated by code.

Every number in a writeup should come from a file produced by a script.
`projects/p2_systems/tables.py` pivots a sweep's JSONL into Markdown or LaTeX, which your report
then `\input`s. Copying numbers by hand is how mismatched units and stale results get into papers.

``` {#lst:perf:sweep .bash caption="A sweep from grid to LaTeX table."}
$ cat grid.json
{"cfg": ["gpt-small", "gpt-medium"], "T": [256, 512, 1024],
 "dtype": ["fp32", "bf16"]}
$ python projects/p2_systems/sweep.py --grid grid.json --out runs.jsonl -- \
    python labs/lab17_perf/bench.py model --cfg {cfg} --T {T} \
    --dtype {dtype} --jsonl /dev/stdout
$ python projects/p2_systems/tables.py runs.jsonl --rows cfg T --cols dtype \
    --value ms_mean --latex \
    > report/step_time.tex
```

## Timing GPU code honestly {#sec:perf:timing}

[@sec:pytorch:async] showed that kernel launches are asynchronous: `torch.matmul` returns
as soon as the kernel is *queued*. A timer around it measures launch overhead, not work.
[@lst:perf:timefn] is the timing loop used throughout the chapter (it lives in
`llmsys/perf.py`); it extends [@lst:pytorch:bench] by returning the full distribution.

``` {#lst:perf:timefn .python caption="Warm up, synchronise, repeat, keep every sample."}
def time_fn(fn, warmup=5, iters=10, sync=synchronize):
    for _ in range(warmup):            # absorb one-off costs
        fn()
    sync()                             # drain everything queued so far
    times = []
    for _ in range(iters):
        t0 = timeit.default_timer()    # highest-resolution monotonic clock
        fn()
        sync()                         # wait for *this* call's kernels
        times.append(timeit.default_timer() - t0)
    return dict(mean=statistics.fmean(times), std=statistics.pstdev(times),
                median=statistics.median(times), min=min(times), times=times)
```

![Left: the CPU races ahead of the GPU. A timer stopped right after the launches measures almost
nothing; synchronising first makes the CPU wait for the queue to drain. Right (schematic): the first
iterations are slower and must be excluded from the
statistics.](figures/ch17_perf_engineering-2.svg){#fig:perf:timeline}

##### What warm-up absorbs.

The first call to a model on a fresh process pays for things that never recur: CUDA context creation
and module loading (hundreds of milliseconds), cuBLAS/cuDNN heuristic selection or autotuning for
each new shape, Triton JIT compilation and autotuning, `torch.compile` tracing and code generation
(seconds to minutes), growth of the caching allocator's pool (each new block is a `cudaMalloc`), and
GPU clock ramp-up from idle. If the first few samples differ from the rest, which they nearly always
do, either discard them or report them separately as "time to first step", a number that matters for
short jobs and for serving cold starts.

##### Variance and what to report.

Report a central value *and* a spread: the mean with standard deviation if the samples look
Gaussian, otherwise the median with percentiles. Large spread usually has a cause: another process
on the GPU, thermal or power throttling (`nvidia-smi -q -d PERFORMANCE` shows the throttle reasons),
host-side Python work that is sometimes on the critical path, or data-dependent work (e.g. a
variable number of tokens).

##### CUDA events and `do_bench`.

Wall-clock timing includes host overhead between synchronisations. CUDA events
(`torch.cuda.Event(enable_timing=True)`) are timestamps written by the GPU into its own stream, so
the elapsed time between two events measures device time only (`perf.cuda_event_time`). Triton's
`triton.testing.do_bench` goes further: it estimates how many repetitions fit in a time budget,
clears the L2 cache between repetitions by writing a large buffer (so a kernel cannot benefit from
data left in cache by its previous run), and returns a robust statistic. `perf.bench` uses it on
GPUs and falls back to `time_fn` elsewhere. Use events or `do_bench` for individual kernels and
wall-clock timing for whole training steps, where host overhead is part of what you want to measure.

::: napkinmath
[What should a forward pass cost?]{.box-title}

Before timing anything, predict the answer. GPT-2 medium has $3.53\times10^{8}$ parameters, of which
$3.02\times10^8$ are outside the embeddings. A batch of $B=4$ sequences of $T=512$ tokens is 2048
tokens; with $\approx2N$ FLOPs per token plus the attention term (`flops.flops_per_token_forward`)
the forward pass needs about $1.55\times10^{12}$ FLOPs. At the H100's 989 TFLOP/s bf16 peak that is
1.6 ms; a realistic 40--60% of peak gives 2.6--3.9 ms. In fp32 without TF32 the matmuls run on the
CUDA cores at roughly 67 TFLOP/s, so expect about 15 times longer. A measurement far outside these
bounds means either the measurement or your understanding is wrong, and both are worth knowing.
:::

## Profiling with Nsight Systems and NVTX {#sec:perf:nsys}

A timer says *how long*; a profiler says *where*. Python profilers such as `cProfile` see only the
host side: they attribute time to the function that *launched* a kernel, which is the wrong place.
NVIDIA Nsight Systems (`nsys`) instruments the CUDA driver through CUPTI and records, on one
timeline, the host threads, every CUDA API call, every kernel and memory copy on the device, NCCL
communication, OS runtime events, and user-defined *NVTX ranges*. Nsight Compute (`ncu`) is its
microscope: it replays a single kernel many times to read hardware counters (achieved occupancy,
memory throughput per level, tensor-pipe utilisation, warp stall reasons) and places the kernel on a
roofline.

### Collecting a profile

``` {#lst:perf:nsys .bash caption="Profiling only the measured iterations."}
nsys profile -o step_bf16 \
  --trace=cuda,nvtx,osrt,cublas,cudnn \
  --pytorch=functions-trace,autograd-shapes-nvtx \
  --capture-range=nvtx --nvtx-capture=measure --capture-range-end=stop \
  python labs/lab17_perf/bench.py model --cfg gpt-medium --T 512 \
         --dtype bf16 --nvtx
nsys stats --report cuda_gpu_kern_sum step_bf16.nsys-rep  # kernel summary
```

The flags are worth understanding rather than copying. `--trace` chooses which APIs to record; every
additional source adds overhead. `--pytorch=functions-trace` makes recent `nsys` versions emit an
NVTX range per PyTorch operator and `autograd-shapes-nvtx` labels autograd nodes with tensor shapes;
both are convenient, and both slow the run. The capture-range options start recording only when an
NVTX range named `measure` opens, so warm-up iterations (and their compile and autotune kernels)
never pollute the profile. Backtrace options (`--cudabacktrace`, `--python-backtrace`) tell you
which line launched each kernel at a large overhead: enable them for a targeted question, not by
default. The `.nsys-rep` file opens in the Nsight Systems GUI on any laptop, so you can profile on a
remote GPU node and inspect the result locally.

### Annotating your code

NVTX ranges are cheap host-side push/pop markers. They appear as labelled bars above the CUDA API
row, and the GUI can filter every statistic by range. `llmsys.perf` provides a context manager that
emits both an NVTX range (for Nsight) and a `record_function` scope (for `torch.profiler`), plus a
helper that annotates module calls automatically with hooks:

``` {#lst:perf:nvtx .python caption="NVTX annotation by hand and by hooks (from `llmsys/perf.py`)."}
@contextlib.contextmanager
def nvtx_range(name):
    if torch.cuda.is_available():
        torch.cuda.nvtx.range_push(name)
    try:
        with torch.profiler.record_function(name):
            yield
    finally:
        if torch.cuda.is_available():
            torch.cuda.nvtx.range_pop()

def annotate_modules(model, types=()):
    nvtx, handles = torch.cuda.nvtx, []
    for name, mod in model.named_modules():
        if mod is model or (types and not isinstance(mod, tuple(types))):
            continue
        handles += [mod.register_forward_pre_hook(
                        lambda m, a, l=name: nvtx.range_push("fwd:" + l)),
                    mod.register_forward_hook(lambda m, a, o: nvtx.range_pop()),
                    mod.register_full_backward_pre_hook(
                        lambda m, g, l=name: nvtx.range_push("bwd:" + l)),
                    mod.register_full_backward_hook(
                        lambda m, gi, go: nvtx.range_pop())]
    return handles

# inside an attention implementation:
with nvtx_range("attn/scores"):  s = q @ k.transpose(-1, -2) * scale
with nvtx_range("attn/softmax"): p = torch.softmax(s, dim=-1)
with nvtx_range("attn/pv"):      o = p @ v
```

To annotate code you do not own, monkey-patch the function before building the model
(`some_module.attention = annotated_attention`); Python resolves module-level names at call time.
One caveat: `torch.compile` fuses across your annotations and may move work out of a range, so
profile compiled code at the granularity of whole compiled regions.

![What a training step looks like in Nsight Systems (schematic). Host-side launches (CUDA API row)
run ahead of device execution. Large blue GEMM kernels dominate forward and backward; short orange
memory-bound kernels (norms, activations, softmax, elementwise) fill the gaps. In an unfused
optimizer step, hundreds of tiny kernels leave the GPU idle between launches: the signature of a
launch-bound region.](figures/ch17_perf_engineering-3.svg){#fig:perf:nsys}

### Reading the timeline

Four questions cover most investigations. **Is the GPU ever idle?** White space in the kernel row
while the host row is busy means the host cannot launch fast enough (launch-bound: too many small
kernels, Python overhead, a synchronisation such as `.item()`); white space in both rows means the
host is waiting for something else (data loading, I/O, a collective). **Which kernels dominate?**
The *CUDA GPU Kernel Summary* (`nsys stats` or the GUI's Stats view) ranks kernels by total time;
filter it by NVTX range to split forward from backward from optimizer. GEMM kernels have
recognisable names (`sm90_xmma_gemm_…`, `cutlass_…`, `ampere_…_gemm`), and Triton kernels carry
their Python function name. **Does the host match the device?** Clicking a CUDA API call highlights
the kernel it launched, which shows the queue depth: how far ahead the CPU is running. **Is
communication overlapped?** NCCL kernels concurrent with compute kernels on another stream are free;
NCCL kernels alone on the timeline are not.

::: systemslens
[FLOPs are not time]{.box-title}

In a transformer forward pass more than 95% of FLOPs are in GEMMs, but a profile typically shows
non-GEMM kernels taking a much larger share of time, often 20--40% for small models in fp32 and more
in bf16, where the GEMMs got faster but the elementwise kernels did not. The reason is arithmetic
intensity ([@sec:pytorch:roofline]): a softmax over a $T\times T$ score matrix does a
handful of FLOPs per element and moves every element through HBM at least twice, whereas the matmul
that produced it does $2d_{h}$ FLOPs per element. With $d_{h}=64$ that is a FLOP ratio of roughly
$50\times$ in the matmul's favour but a *time* ratio that can be close to $1\times$, because both
are paying for the same bytes. Fusion ([@sec:perf:residuals]) and FlashAttention
([@sec:perf:fa2]) attack exactly this gap.
:::

## Where the time goes in a training step {#sec:perf:anatomy}

::: {#tab:perf:classes .table-float}
| kernel class | examples | FLOPs/byte (bf16) | usually |
|:---|:---|:---|:---|
| GEMM | QKV/out projections, MLP, LM head | $\approx\frac{mnk}{mk+kn+mn}$, hundreds | compute-bound |
| attention core | $\mathbf{Q}\mathbf{K}^\top$, softmax, $\mathbf{P}\mathbf{V}$ (unfused) | GEMMs high, softmax $\sim1$ | mixed |
| normalisation | LayerNorm, RMSNorm | $\sim1$--3 | memory-bound |
| activation | GELU, SiLU$\cdot$gate | $<1$--2 | memory-bound |
| residual / dropout / casts | add, mask, `.to(bf16)` | $<1$ | memory-bound |
| loss | log-softmax over $V$, gather | $\sim1$ | memory-bound, huge |
| optimizer | AdamW over all parameters | $\approx0.5$ | memory-bound |

: Kernel classes in a transformer training step, with typical arithmetic intensity (analytic). Only
the GEMMs can approach the tensor-core roofline; everything else is limited by HBM bandwidth, so its
cost is set by the bytes it moves.
:::

[@tab:perf:classes] is the mental model to bring to a profile. Three non-obvious entries
deserve comment.

##### The loss.

The LM head produces $B\cdot T\cdot V$ logits. For Qwen3's vocabulary ($V=151{,}936$) and a modest
batch of $4\times2048$ tokens, that is 2.5 GB in bf16 and 5.0 GB once upcast to fp32 for a stable
log-softmax, plus the same again for its gradient. The FLOPs are trivial; the bytes are not.
[@sec:perf:playbook] shows how to avoid materialising them.

##### The optimizer.

An unfused AdamW step reads the parameter, gradient and two moments and writes back the parameter
and both moments: about 28 bytes per fp32 parameter. For 1.3B parameters that is 36 GB of HBM
traffic, or 11 ms at the H100's 3.35 TB/s *if* the kernels saturate bandwidth, which tiny per-tensor
kernels do not. The forward and backward passes of the same model on $8\times2048$ tokens need about
130 ms at peak, so the optimizer is a visible slice of the step, larger the smaller the batch.
PyTorch's `foreach` implementation (the default) batches tensors into a few multi-tensor kernels;
`fused=True` goes further and does the whole update in one kernel per parameter group.

##### Backward is about twice forward.

Each linear layer $\mathbf{Y}=\mathbf{X}\mathbf{W}$ needs $\mathbf{dX}=\mathbf{dY}\mathbf{W}^\top$
and $\mathbf{dW}=\mathbf{X}^\top\mathbf{dY}$ in backward: two GEMMs of the same size as the one in
forward. Elementwise ops are similar or worse, because their backward reads saved inputs *and* the
incoming gradient. Expect backward time of $1.8$--$2.5\times$ forward; a much larger ratio points at
an inefficient backward kernel (classically attention, or an op with a scatter in its gradient).

::: systemslens
[Tile and wave quantisation]{.box-title}

GEMM throughput is not a smooth function of shape. A GEMM kernel covers the output with tiles
(e.g. $128\times256$); a dimension that is one more than a multiple of the tile size launches a
whole extra row of mostly empty tiles (*tile quantisation*). The tiles then run in *waves* of one
tile per SM: 133 tiles on a 132-SM H100 take two waves, the second with a single busy SM (*wave
quantisation*). Hence the folklore of padding $d_{\text{model}}$, $d_{\text{ff}}$, vocabulary and
per-GPU batch $\times$ sequence to multiples of 64 or 128, and of looking at throughput as a
function of size before choosing a model's shape (Exercise [-@ex:perf:waves]). Memory-access
alignment adds a third effect: rows whose byte stride is not a multiple of the DRAM burst and
vector-load width force uncoalesced loads.
:::

## Mixed precision in practice {#sec:perf:amp}

[@sec:pretrain:mixed] introduced the recipe: bf16 matmuls under `torch.autocast`, fp32
master weights, loss scaling only for fp16. Here we look at what autocast actually does to a block,
why accumulation precision matters more than storage precision, and what changes in memory.

##### Autocast is a per-op policy.

Inside `torch.autocast(device_type, dtype)`, each operator consults a list. Ops that benefit from
tensor cores and are numerically safe in 16 bits (`mm`, `addmm`, `bmm`, `linear`, convolutions,
SDPA) cast their inputs to the low-precision dtype. Ops that are numerically sensitive (reductions
such as `sum` and `mean`, `softmax`/`log_softmax`, `layer_norm`, losses, `exp`, `pow`) run in fp32.
Everything else runs in the widest dtype among its inputs. Parameters stay fp32; autocast casts a
weight once per forward pass and caches the copy, so gradients flow back into the fp32 parameter.

![dtype flow through a pre-norm block under `torch.autocast(dtype=torch.bfloat16)`. Exact lists
differ by PyTorch version and backend (check `torch.amp.autocast_mode`); the pattern is stable:
matmuls go to bf16, reductions and losses stay fp32, and the fp32 residual stream promotes bf16
branch outputs back to fp32.](figures/ch17_perf_engineering-4.svg){#fig:perf:amp}

##### Accumulate wide, store narrow.

The danger in low precision is not storing a number in 16 bits; it is adding many small numbers into
a 16-bit running sum. Once the sum is large, each addend is smaller than half a unit in the last
place of the sum and is rounded away. A measurement in this environment: adding $10^{-3}$ ten
thousand times gives 9.9945 with an fp32 accumulator (the error is just bf16's rounding of $10^{-3}$
itself), 4.0 with an fp16 accumulator, and 0.5 with a bf16 accumulator. bf16 has fp32's *range* but
only 8 bits of *precision*, so it stagnates sooner than fp16. This is why tensor cores multiply
16-bit inputs but accumulate in fp32, why every reduction in a kernel (the row sums $\ell$ and the
output accumulator in FlashAttention, the variance in RMSNorm) should be kept in fp32 registers, and
why `torch.sum` on a bf16 tensor accumulates internally in fp32.

##### fp16 versus bf16 for normalisation.

With fp16, the mean of squares in an RMSNorm can overflow (squares of activations above $\sim256$
exceed fp16's 65,504) and small variances can underflow; this is why autocast runs norms in fp32.
bf16 removes the range problem but not the precision one, so the statistic should still be computed
in fp32, which is what `llmsys.layers.RMSNorm` does explicitly.

::: pitfall
[Mixed precision can *increase* memory]{.box-title}

Autocast keeps fp32 parameters *and* caches bf16 copies of the weights during the forward pass, and
the bf16 activations saved for backward are only half of what they would be in fp32 if the saved
tensors are actually bf16. Some are not: the fp32 residual stream and the inputs of fp32-forced ops
stay fp32. For small models, where weights rather than activations dominate memory, peak memory
under autocast can be equal to or slightly higher than in pure fp32. The large memory wins come from
*storing* parameters in bf16 (with fp32 master copies held only by the optimizer, or sharded as in
[@ch:sharding]) and from bf16 activations at long contexts. Measure it with
[@sec:perf:memory]'s tools instead of assuming it.
:::

``` {#lst:perf:ampknobs .python caption="Precision switches worth knowing."}
torch.backends.cuda.matmul.allow_tf32 = True     # fp32 GEMMs on tensor cores (TF32)
torch.set_float32_matmul_precision("high")        # same, newer spelling
with torch.autocast("cuda", dtype=torch.bfloat16):
    loss = loss_fn(model(x), y)                   # matmuls bf16, reductions fp32
loss.backward()                                   # grads land in fp32 .grad
# fp16 needs dynamic loss scaling:
scaler = torch.amp.GradScaler("cuda")
scaler.scale(loss).backward(); scaler.step(opt); scaler.update()
```

## Where the memory goes {#sec:perf:memory}

GPU memory during training has five tenants: **parameters**; **gradients** (one per parameter,
allocated on the first backward pass); **optimizer state** (two fp32 moments for AdamW);
**activations** saved for backward (the only tenant that scales with batch size and sequence
length); and **temporaries** (workspace for GEMMs, intermediate results that die immediately,
communication buffers). On top of them sits the *caching allocator* ([@sec:pytorch:async]):
freed blocks stay reserved for reuse, so `torch.cuda.memory_reserved()` exceeds
`memory_allocated()`, and a fragmented pool can fail an allocation even when the total free memory
would suffice.

::: napkinmath
[A memory budget before the first run]{.box-title}

For a model with $N$ parameters trained with AdamW in fp32 the static tenants take $4+4+8=16$ bytes
per parameter, so 1.3B parameters need 20.8 GB before a single activation is stored. Activations
scale with tokens: one $(B,T,d_{\text{model}})$ residual-stream tensor for Qwen3-0.6B
($d_{\text{model}}=1024$) at $B=4$, $T=2048$ in fp32 is $4\cdot2048\cdot1024\cdot4$ B $=32$ MiB, and
a transformer block saves tens of such tensors ([@sec:perf:residuals]). With 28 blocks and
$\sim$`<!-- -->`{=html}30 units per block that is about 27 GiB of activations: activations, not
weights, dominate once batches are realistic. That is why the checkpointing of
[@sec:perf:ckpt] matters.
:::

### Memory snapshots

PyTorch can record every allocation and free with a stack trace and dump the history for an
interactive viewer at <https://pytorch.org/memory_viz>. `llmsys.perf.memory_snapshot` wraps the
private-but-stable API:

``` {#lst:perf:snapshot .python caption="Recording an allocator history for the memory viewer."}
@contextlib.contextmanager
def memory_snapshot(path="memory_snapshot.pickle", max_entries=1_000_000):
    torch.cuda.memory._record_memory_history(max_entries=max_entries)
    try:
        yield
    finally:
        torch.cuda.memory._dump_snapshot(path)
        torch.cuda.memory._record_memory_history(enabled=None)

for _ in range(warmup): step()          # do NOT record warm-up allocations
with memory_snapshot("step.pickle"):
    step()                              # one forward + backward + optimizer step
print(torch.cuda.max_memory_allocated() / 2**30, "GiB peak")
```

Activations grow linearly through the forward pass, peak around the loss (where the logits and their

## What autograd saves, and why fusion helps {#sec:perf:residuals}

Every differentiable op decides which tensors its backward needs and stores them on the graph: the
*saved tensors* or *residuals*. `linear` saves its input (to compute
$\mathbf{dW}=\mathbf{X}^\top\mathbf{dY}$) and a view of its weight; `softmax` saves its output; a
multiplication saves both operands; `dropout` saves its mask. A composite written from primitives
saves the residuals of every primitive, and many of them are full-size activations.

PyTorch exposes the mechanism through `torch.autograd.graph.saved_tensors_hooks(pack, unpack)`:
`pack` is called on every tensor being saved and may return anything (the tensor itself, a
compressed copy, a handle to host memory); `unpack` reverses it during backward.
`SavedTensorTracker` ([@lst:perf:tracker]) uses a pass-through `pack` to account for bytes,
counting each storage once and skipping parameters and views of parameters (`linear` saves
`weight.T`, a view whose `_base` is the parameter).

``` {#lst:perf:tracker .python caption="Accounting for residuals with saved-tensor hooks (abridged from `llmsys/perf.py`)."}
class SavedTensorTracker:
    def _pack(self, t):
        base = getattr(t, "_base", None)
        if isinstance(t, nn.Parameter) or isinstance(base, nn.Parameter):
            return t                                     # resident anyway
        st = t.untyped_storage()
        key = (st.data_ptr(), st.nbytes())               # count each storage once
        nbytes = 0 if key in self._seen else st.nbytes()
        self._seen.add(key)
        gf = type(t.grad_fn).__name__ if t.grad_fn else None
        self.entries.append(dict(shape=tuple(t.shape), dtype=t.dtype,
                                 bytes=nbytes, grad_fn=gf))
        return t
    def __enter__(self):
        hooks = torch.autograd.graph.saved_tensors_hooks
        self._h = hooks(self._pack, lambda t: t)
        self._h.__enter__(); return self

with SavedTensorTracker() as tr:
    y = block(x)                                         # forward only
print(tr.total_bytes / 2**20, "MiB saved for backward"); print(tr.table())
```

Two lessons are visible. First, the tanh-approximated GELU written as a formula
([@sec:gpt:ffn]) saves four or five $4d_{\text{model}}$-wide intermediates, each four times
the size of the residual stream: the activation function alone outweighs everything else in the MLP.
Second, the attention probabilities appear twice. The second copy comes from a defensive
`torch.nan_to_num` in the core attention (it zeroes rows that are entirely padding,
[@ch:serving]): an innocent-looking op that, in training, costs one more $B\cdot H\cdot T^2$
tensor per layer. Residual accounting finds such costs immediately; reading the code rarely does.

![Bytes saved for backward by one GPT-2-small block ($B=2$, $T=256$, fp32), measured in this

##### Why fusion reduces residuals.

When an op is fused into one kernel with its own backward, autograd sees a single node and saves
only what that node's backward needs. A fused RMSNorm needs only its input, weight and per-row
inverse RMS (a $B\times T\times1$ tensor), not the four intermediates of the unfused formula.
`torch.compile` achieves this automatically: AOTAutograd traces forward and backward together into
one joint graph, and a *min-cut partitioner* decides which intermediates to save and which to
recompute in the backward kernel, choosing to recompute cheap pointwise ops whose outputs would be
expensive to store ([@fig:perf:residuals]). The same principle, applied by hand to
attention, is FlashAttention: save $\mathbf{O}$ and a per-row statistic, never $\mathbf{P}$.

## Activation checkpointing in depth {#sec:perf:ckpt}

[@sec:pretrain:efficiency] introduced checkpointing and the $\sqrt L$ rule. Here we make
the cost model precise and measure it. Wrapping a function in
`torch.utils.checkpoint.checkpoint(fn, x, use_reentrant=False)` changes two things: in the forward
pass, $\texttt{fn}$ runs without saving residuals (only its input $x$ is kept); in the backward
pass, before gradients flow through $\texttt{fn}$, the forward is re-run from $x$ with saving
enabled, and its residuals are consumed and freed immediately.

``` {#lst:perf:ckptseg .python caption="Checkpointing groups of blocks (from `llmsys/perf.py`)."}
def checkpoint_segments(blocks, x, segment):
    if segment <= 0:
        for b in blocks: x = b(x)
        return x
    def run(lo, hi):
        def f(h):
            for b in blocks[lo:hi]: h = b(h)
            return h
        return f
    for lo in range(0, len(blocks), segment):
        hi = min(lo + segment, len(blocks))
        x = checkpoint(run(lo, hi), x, use_reentrant=False)
    return x
```

##### The cost model.

Let a stack have $L$ identical blocks, each with input size $a$ and residual size $A$ (both in
bytes). Checkpointing groups of $k$ blocks stores $L/k$ group inputs for the whole step; during
backward, one group at a time is recomputed and its $kA$ residuals are alive. Ignoring smaller
terms, the peak is $$\begin{equation}
M(k) \approx \frac{L}{k}\,a + k\,A,
\qquad
k^\star = \sqrt{\frac{L\,a}{A}},
\qquad
M(k^\star) = 2\sqrt{L\,a\,A}.
\label{eq:perf:ckpt}
\end{equation}$$ The classic $\sqrt L$ result assumes $a\approx A$. In a transformer $A/a$ is
*large*: 16 to 40 in [@fig:perf:residuals]. With $L=12$ and $A/a=32$,
[@eq:perf:ckpt] gives $k^\star\approx0.6$, so the best one-level policy is to checkpoint
*every* block. [@fig:perf:ckpt] confirms it with measured bytes. Recomputation costs one
extra forward per checkpointed block regardless of $k$, about 33% more FLOPs for the stack (a
forward is roughly a third of forward plus backward), so the choice of $k$ is purely about memory.

![One-level checkpointing of a 12-block GPT-2-small stack ($B=2$, $T=256$, fp32, SDPA), measured
with `SavedTensorTracker` via `bench.py ckpt`. Because one block's residuals are 32 times its input,
checkpointing every block ($k=1$) minimises the peak: 66 MiB instead of
579 MiB.](figures/ch17_perf_engineering-7.svg){#fig:perf:ckpt}

##### Beyond one level.

Checkpoints may be nested: a checkpointed group can itself checkpoint its sub-groups, trading
further recomputation for memory. Chen et al. (2016) analyse such schemes; the optimal schedules for
a fixed recomputation budget come from the *revolve* family of algorithms in automatic
differentiation (Griewank and Walther, 2000). Exercise [-@ex:perf:twolevel] works through a
two-level schedule with the cost model above.

##### Selective checkpointing.

Recomputing a whole block re-runs its GEMMs, which are the expensive part. *Selective activation
checkpointing* saves the outputs of expensive ops and recomputes only cheap ones (norms,
activations, elementwise products), keeping most of the memory saving for a few percent of extra
FLOPs (Korthikanti et al., 2022). PyTorch supports it with a per-op policy:

``` {#lst:perf:sac .python caption="Selective activation checkpointing: keep matmul outputs, recompute the rest."}
from torch.utils.checkpoint import (checkpoint, CheckpointPolicy,
                                    create_selective_checkpoint_contexts)
aten = torch.ops.aten
SAVE = {aten.mm.default, aten.addmm.default, aten.bmm.default,
        aten._scaled_dot_product_flash_attention.default}

def policy(ctx, op, *args, **kwargs):
    if op in SAVE:
        return CheckpointPolicy.MUST_SAVE
    return CheckpointPolicy.PREFER_RECOMPUTE

y = checkpoint(block, x, use_reentrant=False,
               context_fn=lambda: create_selective_checkpoint_contexts(policy))
```

##### Offloading.

A third option is to move residuals to host memory during forward and fetch them back during
backward, with `saved_tensors_hooks` whose `pack` copies to pinned host memory
(`perf.offload_saved_tensors`, or PyTorch's `torch.autograd.graph.save_on_cpu`). It costs no FLOPs
but needs bandwidth: at PCIe Gen5's $\sim$`<!-- -->`{=html}50 GB/s, offloading 1 GB of residuals per
layer adds 40 ms of transfers per layer per step, which hides behind compute only for very large
layers. It is attractive on systems with a fast CPU--GPU link (NVLink-C2C on Grace Hopper reaches
several hundred GB/s).

::: pitfall
[Reentrant checkpointing and RNG]{.box-title}

Always pass `use_reentrant=False`. The older reentrant implementation does not support inputs that
do not require gradients, keyword arguments or nested structures, and it interacts badly with
`torch.compile`. Recomputation also re-runs random ops: dropout must produce the same mask twice, so
`checkpoint` saves and restores the RNG state (`preserve_rng_state=True`, the default). Code that
consumes global random numbers inside a checkpointed region in a data-dependent way breaks this
guarantee.
:::

## torch.compile in practice {#sec:perf:compile}

`torch.compile` ([@sec:pytorch:async]) has three stages. **Dynamo** executes your Python
bytecode, records the PyTorch ops into an FX graph, and inserts *guards* (assumptions about shapes,
dtypes, Python values) that decide when the compiled code can be reused. **AOTAutograd** traces the
backward too and partitions the joint graph. **Inductor** lowers the graph to Triton kernels on GPU
(C++/OpenMP on CPU), fusing chains of pointwise and reduction ops and calling cuBLAS or generated
templates for matmuls.

``` {#lst:perf:compilelogs .bash caption="Seeing what the compiler did."}
TORCH_LOGS="graph_breaks,recompiles" python train.py  # why graphs split/recompile
TORCH_LOGS="output_code" python train.py              # generated Triton kernels
TORCH_COMPILE_DEBUG=1 python train.py                 # full dump to a debug dir
```

Five practical rules follow from that architecture. **Avoid graph breaks** in hot code: `print`,
`.item()`, data-dependent Python control flow and unsupported libraries end the graph, and each
break is a lost fusion opportunity plus a return to the interpreter; `fullgraph=True` turns breaks
into errors so you find them. **Avoid recompilation**: a new shape invalidates a shape guard;
`dynamic=True` or `torch._dynamo.mark_dynamic` compiles shape-polymorphic code, and padding sequence
lengths to a few buckets keeps the number of variants small. **Compile the right unit**: compiling
each transformer block separately (`block.compile()`) gives the same fusions as the whole model with
a fraction of the compile time, because all blocks share one compiled artifact. **Budget compile
time**: the first step can take minutes for a large model with `mode="max-autotune"`, which
benchmarks GEMM templates and enables CUDA graphs; use it for long jobs, not for quick experiments.
**Profile after compiling**: fused kernels get generated names (`triton_poi_fused_add_mul_0`), so
map them back with `TORCH_LOGS=output_code` or by compiling smaller regions.

::: deepdive
[CUDA graphs]{.box-title}

When a step is launch-bound ([@fig:perf:nsys]), the fix is to stop launching. A CUDA graph
records a sequence of kernel launches with fixed arguments once and replays it with a single launch.
Requirements follow from "fixed arguments": static shapes, static memory addresses (inputs are
copied into preallocated buffers), and no host synchronisation inside the captured region.
`torch.compile(mode="reduce-overhead")` applies CUDA graphs automatically; [@ch:inference]
uses them for decoding, the most launch-bound workload in this book.
:::

## Attention at long context {#sec:perf:attn}

Attention's cost model is in [@sec:attention:cost]; here we turn it into a benchmarking
plan. The experiment to run is a grid over head dimension $d_{h}$ and sequence length $T$ for each
implementation (eager, compiled, SDPA, our FlashAttention-2), recording forward time, backward time
and memory in use before the backward starts (`bench.py attention`). Two outcomes are worth
predicting before you look.

##### Memory.

An eager implementation saves the probabilities $\mathbf{P}$ ($B\cdot H\cdot T^2$ elements) plus the
mask, $\mathbf{Q}$, $\mathbf{K}$ and $\mathbf{V}$; the closed form, which Lab 16 asks you to derive
and verify, is exact. For Qwen3-0.6B ($H=16$) at $T=8192$ in fp32, $\mathbf{P}$ alone is 4.3 GB per
layer, 120 GB for 28 layers: no single GPU holds it, which is why naive attention runs out of memory
at sequence lengths where the weights are still tiny. The quadratic term is the only one that
matters at long context, and it grows $4\times$ for every doubling of $T$.

##### Time.

`torch.compile` fuses the scale, mask and softmax into fewer kernels and can save fewer residuals,
but it cannot remove the $T^2$ tensor that one GEMM writes and the next reads, so compiled eager
attention stays memory-bound and runs out of memory at about the same length. Removing the quadratic
traffic needs a kernel that never writes $\mathbf{S}$ or $\mathbf{P}$ to HBM: FlashAttention.

## FlashAttention-2 in Triton, forward and backward {#sec:perf:fa2}

[@sec:attention:flash] derived the online softmax and the recomputation backward and
implemented both in tiled PyTorch; [@sec:triton:flash] wrote a forward-only Triton kernel.
This section completes the job: a kernel set that can *train*, in `llmsys/kernels/flash2_triton.py`,
with a loop-for-loop PyTorch model in `flash2_ref.py` for debugging.

### What FlashAttention-2 changes

Three changes relative to the original algorithm matter for an implementation (Dao, 2023). **Loop
order.** The outer loop runs over query tiles and the inner over key tiles, so each program owns one
query tile and keeps its output accumulator, row maximum $m$ and row sum $\ell$ in registers for the
whole inner loop; nothing is written to HBM until the end. **Deferred normalisation.** The
accumulator is kept unnormalised and divided by $\ell$ once at the end, saving one division per
element per key tile. Non-matmul FLOPs are expensive on tensor-core GPUs, so this matters.
**Parallelism over the sequence.** The grid is (query tiles) $\times$ (batch $\cdot$ heads), so long
sequences with few heads still fill all SMs.

The forward also writes one extra number per query row, the log-sum-exp $$\begin{equation}
L_i = m_i + \log \ell_i = \log\sum_j \exp(S_{ij}),
\label{eq:perf:lse}
\end{equation}$$ because it is all the backward needs to rebuild any tile of probabilities exactly:
$P_{ij}=\exp(S_{ij}-L_i)$.

![Work decomposition for causal attention with equal tile sizes. A forward (or dQ) program owns a
row of tiles and processes them in two stages: fully visible tiles without any masking arithmetic,
then the diagonal tile with a mask. A dK/dV program owns a column and visits only the rows at or
below the diagonal. With $n$ tiles per side, $n(n+1)/2$ of the $n^2$ tiles are visited and only $n$
need a mask.](figures/ch17_perf_engineering-8.svg){#fig:perf:tiles}

### Pointers, tiles and a note on block pointers {#sec:perf:fa2:blockptr}

Each tensor is reshaped to $(B\cdot H, T, D)$ and made contiguous, so element $(b, t, d)$ lives at
`base + b*stride_h + t*stride_t + d`. A tile of rows `offs_m` is loaded with a 2-D pointer grid
`base + offs_m[:, None]*stride_t + offs_d[None, :]` and a mask for the ragged last tile. Triton has
also offered structured alternatives that carry shape, strides and offsets together and let the
compiler emit bulk copies: *block pointers* (`tl.make_block_ptr` with `.advance`) in Triton 2.x--3.x
releases, and *tensor descriptors* (`tl.make_tensor_descriptor`), which map onto Hopper's and
Blackwell's Tensor Memory Accelerator (TMA). Recent Triton releases removed block pointers in favour
of tensor descriptors (the version installed while writing this chapter raises `NotImplementedError`
on `make_block_ptr`). The reference kernels therefore use explicit pointer arithmetic, which every
version supports. When targeting a recent GPU and a recent Triton, porting the loads to descriptors
is the first step towards TMA-based pipelining.

### The forward kernel

``` {#lst:perf:fa2inner .python caption="FA2 forward: the inner loop over key tiles (`flash2_triton.py`, reflowed)."}
@triton.jit
def _fa2_fwd_inner(acc, l_i, m_i, q, k_base, v_base, stride_kt, stride_vt,
                   start, end, offs_m, offs_d, shift, S, scale,
                   BLOCK_N: tl.constexpr, MASK_CAUSAL: tl.constexpr):
    for n0 in range(start, end, BLOCK_N):
        offs_n = n0 + tl.arange(0, BLOCK_N)
        kv_mask = offs_n[:, None] < S                 # ragged last key tile
        k = tl.load(k_base + offs_n[:, None] * stride_kt + offs_d[None, :],
                    mask=kv_mask, other=0.0)
        v = tl.load(v_base + offs_n[:, None] * stride_vt + offs_d[None, :],
                    mask=kv_mask, other=0.0)
        s = tl.dot(q, tl.trans(k)) * scale            # fp32 scores tile
        keep = offs_n[None, :] < S
        if MASK_CAUSAL:                               # stage 2 only
            keep = keep & (offs_n[None, :] <= offs_m[:, None] + shift)
        s = tl.where(keep, s, float("-inf"))
        m_new = tl.maximum(m_i, tl.max(s, axis=1))
        p = tl.exp(s - m_new[:, None])
        alpha = tl.exp(m_i - m_new)                   # rescale old stats
        l_i = l_i * alpha + tl.sum(p, axis=1)
        acc = acc * alpha[:, None]
        acc = tl.dot(p.to(v.dtype), v, acc=acc)       # fp32 accumulator
        m_i = m_new
    return acc, l_i, m_i
```

``` {#lst:perf:fa2fwd .python caption="FA2 forward: one program per (query tile, batch$\\times$head), reflowed."}
@triton.jit
def _fa2_fwd_kernel(Q, K, V, O, L, stride_qh, stride_qt, stride_kh, stride_kt,
                    stride_vh, stride_vt, stride_oh, stride_ot, stride_lh,
                    T, S, scale, D: tl.constexpr, BLOCK_M: tl.constexpr,
                    BLOCK_N: tl.constexpr, CAUSAL: tl.constexpr):
    pid_m, bh = tl.program_id(0), tl.program_id(1)
    offs_m = pid_m * BLOCK_M + tl.arange(0, BLOCK_M)
    offs_d = tl.arange(0, D)
    q_mask = offs_m[:, None] < T
    q = tl.load(Q + bh * stride_qh + offs_m[:, None] * stride_qt
                + offs_d[None, :], mask=q_mask, other=0.0)
    kb, vb = K + bh * stride_kh, V + bh * stride_vh
    m_i = tl.full((BLOCK_M,), float("-inf"), dtype=tl.float32)
    l_i = tl.zeros((BLOCK_M,), dtype=tl.float32)
    acc = tl.zeros((BLOCK_M, D), dtype=tl.float32)
    shift = S - T                  # queries are the last T of S positions
    args = (offs_m, offs_d, shift, S, scale, BLOCK_N)   # (spelled out in file)
    if CAUSAL:
        full = (pid_m * BLOCK_M + shift + 1) // BLOCK_N * BLOCK_N
        full = tl.minimum(tl.maximum(full, 0), S)
        diag = tl.minimum((pid_m + 1) * BLOCK_M + shift, S)
        acc, l_i, m_i = _fa2_fwd_inner(acc, l_i, m_i, q, kb, vb, stride_kt,
                                       stride_vt, 0, full, *args, False)
        acc, l_i, m_i = _fa2_fwd_inner(acc, l_i, m_i, q, kb, vb, stride_kt,
                                       stride_vt, full, diag, *args, True)
    else:
        acc, l_i, m_i = _fa2_fwd_inner(acc, l_i, m_i, q, kb, vb, stride_kt,
                                       stride_vt, 0, S, *args, False)
    acc = acc / l_i[:, None]                              # normalise once
    tl.store(O + bh * stride_oh + offs_m[:, None] * stride_ot + offs_d[None, :],
             acc.to(O.dtype.element_ty), mask=q_mask)
    tl.store(L + bh * stride_lh + offs_m, m_i + tl.log(l_i), mask=offs_m < T)
```

(The listing condenses the repeated arguments into `args`; Triton requires them spelled out, as in
the file.) Three details deserve attention. **The two stages** ([@fig:perf:tiles]) share
one inner function; `MASK_CAUSAL` is a `constexpr`, so Triton compiles two specialised copies and
the stage-1 copy contains no comparison at all. Tiles above the diagonal are never loaded, which
halves the work for causal attention. **Masking with $-\infty$** is safe here because every query
row sees at least one key (its own position), so $m$ becomes finite in the first tile that contains
a visible key; kernels that support arbitrary masks, where a row can be fully masked, use a large
negative constant instead and must guard $\ell=0$. **Dtypes**: the dot products take the input dtype
(bf16 on GPU), $p$ is cast to $\mathbf{V}$'s dtype before the second GEMM, and every running
statistic is fp32.

### The backward kernels

With $\mathbf{dO}$ the incoming gradient and $\Delta_i=\sum_d O_{id}\,dO_{id}$ the softmax-Jacobian
row term ([@sec:attention:flash]), the tile-local gradients are $$\begin{gather}
\mathbf{dV}_j \mathrel{+}= \mathbf{P}_{ij}^{\top}\mathbf{dO}_i,\qquad
\mathbf{dP}_{ij}=\mathbf{dO}_i\mathbf{V}_j^{\top},\qquad
\mathbf{dS}_{ij}=\mathbf{P}_{ij}\odot(\mathbf{dP}_{ij}-\Delta_i),\nonumber\\
\mathbf{dQ}_i \mathrel{+}= \tfrac{1}{\sqrt D}\,\mathbf{dS}_{ij}\mathbf{K}_j,\qquad
\mathbf{dK}_j \mathrel{+}= \tfrac{1}{\sqrt D}\,\mathbf{dS}_{ij}^{\top}\mathbf{Q}_i .
\label{eq:perf:fa2bwd}
\end{gather}$$ $\mathbf{dK}_j$ and $\mathbf{dV}_j$ are sums over query tiles, and $\mathbf{dQ}_i$ is
a sum over key tiles. One kernel cannot own both sums without either synchronising across programs
or using atomic adds into $\mathbf{dQ}$ in HBM. Atomics are slow and make the result order-dependent
(non-deterministic bits). The clean solution recomputes $\mathbf{P}$ twice and splits the work:

1.  `_fa2_bwd_preprocess`: one program per query tile computes $\Delta_i$ (a row-wise dot product of
    $\mathbf{O}$ and $\mathbf{dO}$).

2.  `_fa2_bwd_dkdv`: one program per *key* tile loads $\mathbf{K}_j,\mathbf{V}_j$ once, streams the
    query tiles that can see it, and accumulates $\mathbf{dK}_j,\mathbf{dV}_j$ in registers.

3.  `_fa2_bwd_dq`: one program per *query* tile loads $\mathbf{Q}_i,\mathbf{dO}_i,L_i,\Delta_i$,
    streams the visible key tiles, and accumulates $\mathbf{dQ}_i$.

``` {#lst:perf:dkdv .python caption="The dK/dV kernel's loop over query tiles (reflowed)."}
row = lambda X, offs: X + base + offs[:, None] * stride_t + offs_d[None, :]
    start_m = 0
    if CAUSAL:          # query tiles entirely above this key tile cannot see it
        start_m = tl.maximum(pid_n * BLOCK_N - shift, 0) // BLOCK_M * BLOCK_M
    for m0 in range(start_m, T, BLOCK_M):
        offs_m = m0 + tl.arange(0, BLOCK_M)
        rmask = offs_m < T
        q = tl.load(row(Q, offs_m), mask=rmask[:, None], other=0.0)
        do = tl.load(row(DO, offs_m), mask=rmask[:, None], other=0.0)
        lse = tl.load(L + bh * stride_lh + offs_m, mask=rmask, other=0.0)
        delta = tl.load(Delta + bh * stride_lh + offs_m, mask=rmask, other=0.0)
        s = tl.dot(q, tl.trans(k)) * scale
        keep = rmask[:, None] & (offs_n[None, :] < S)
        if CAUSAL:
            keep = keep & (offs_n[None, :] <= offs_m[:, None] + shift)
        p = tl.where(keep, tl.exp(s - lse[:, None]), 0.0)   # P rebuilt from L
        dv = tl.dot(tl.trans(p.to(do.dtype)), do, acc=dv)
        dp = tl.dot(do, tl.trans(v))
        ds = p * (dp - delta[:, None])
        dk = tl.dot(tl.trans(ds.to(q.dtype)), q, acc=dk)
    # after the loop: store dk * scale and dv for this key tile
```

(`row` is shorthand for the pointer grid of a tile of rows; the file writes it out.) The dQ kernel
is the transpose of this pattern: loop over key tiles up to the diagonal, rebuild $\mathbf{P}$, form
$\mathbf{dS}$ and accumulate $\mathbf{dS}\mathbf{K}_j$. Counting GEMMs per visited tile: the forward
does two ($\mathbf{Q}\mathbf{K}^\top$, $\mathbf{P}\mathbf{V}$); the dK/dV kernel four ($\mathbf{S}$,
$\mathbf{dV}$, $\mathbf{dP}$, $\mathbf{dK}$) and the dQ kernel three ($\mathbf{S}$, $\mathbf{dP}$,
$\mathbf{dQ}$), so the backward costs $3.5\times$ the forward in matmul FLOPs, against $2\times$ for
a backward that reads a stored $\mathbf{P}$ and $2.5\times$ for a single-kernel backward that
recomputes $\mathbf{S}$ once. Those extra FLOPs are the price of never touching HBM with a
$T\times T$ tensor, and on memory-bound hardware they are cheap. (FlashAttention-2's reference
implementation instead fuses everything into one kernel and accumulates $\mathbf{dQ}$ with atomics;
both designs are in use.)

### Wiring it into autograd

``` {#lst:perf:fa2fn .python caption="The autograd function: save $(\\mathbf{Q},\\mathbf{K},\\mathbf{V},\\mathbf{O},L)$, never $\\mathbf{P}$."}
class FlashAttention2(torch.autograd.Function):
    @staticmethod
    def forward(ctx, q, k, v, causal=False, block_m=64, block_n=64):
        o, lse = fa2_forward(q, k, v, causal, block_m, block_n)
        ctx.save_for_backward(q, k, v, o, lse)
        ctx.causal, ctx.block_m, ctx.block_n = causal, block_m, block_n
        return o

    @staticmethod
    def backward(ctx, do):
        q, k, v, o, lse = ctx.saved_tensors
        dq, dk, dv = fa2_backward(q, k, v, o, do.contiguous(), lse, ctx.causal,
                                  ctx.block_m, ctx.block_n)
        return dq, dk, dv, None, None, None   # one entry per forward input

out = FlashAttention2.apply(q, k, v, True)    # (B, H, T, D) -> (B, H, T, D)
```

`backward` must return one gradient per `forward` argument, with `None` for non-tensors. The
incoming `do` may be non-contiguous (it is often a transposed view produced by the next layer's
backward), and the kernels assume unit stride in the last dimension, hence the `.contiguous()`.
Saved memory per layer is now $\mathbf{Q},\mathbf{K},\mathbf{V},\mathbf{O}$ plus $B\cdot H\cdot T$
fp32 log-sum-exps: linear in $T$.

### Testing a kernel

Kernel bugs are silent: a wrong stride or an off-by-one mask produces plausible numbers. A test
ladder that catches them in increasing order of difficulty:

1.  **Reference in fp64.** The tiled PyTorch model (`flash2_ref.py`) must match naive attention to
    $10^{-10}$ in float64, and its autograd function must pass `torch.autograd.gradcheck`. This
    validates the *algorithm* independently of Triton.

2.  **Kernel against reference, fp32, interpreter.** On a CPU, `TRITON_INTERPRET=1` (set before
    `triton` is imported) runs each program instance with NumPy semantics; the test suite of Lab 16
    checks $\mathbf{O}$, $L$, $\mathbf{dQ}$, $\mathbf{dK}$, $\mathbf{dV}$ to $10^{-5}$ for causal
    and non-causal inputs, including ragged lengths. In the interpreter you can `print` inside a
    kernel and set breakpoints.

3.  **Kernel on GPU, bf16, against SDPA.** Tolerances widen to $\sim10^{-2}$ absolute: bf16 inputs,
    TF32 or bf16 dot products, and a different summation order. Compare relative error per row, and
    test sizes that are not multiples of the tile sizes.

4.  **End to end.** Swap the kernel into a model and check that the loss curve of a short run
    overlaps the reference within seed-to-seed noise.

### Tuning

Tile sizes trade parallelism for reuse. Larger `BLOCK_M` means fewer re-reads of
$\mathbf{K},\mathbf{V}$ per query (each query tile streams all of them), but more registers per
program and fewer programs to fill the SMs. `num_warps` sets threads per program, and `num_stages`
sets how many tiles the compiler double- or triple-buffers in shared memory to overlap loads with
compute. The best setting depends on $d_{h}$, dtype and GPU, so search it with `triton.autotune`
over a small space (`flash2_triton.autotune_configs()`), keyed on $T$ and $d_{h}$. Autotuning runs
every config at the first call for each key, so cache results and keep the space small when compile
time is budgeted. Further speedups, in roughly increasing effort: use `exp2` with pre-scaled logits
(the hardware has a fast base-2 exponential), process the diagonal tiles in a separate launch, load
$\mathbf{K}/\mathbf{V}$ with TMA tensor descriptors and pipeline with warp specialisation as in
FlashAttention-3 (Shah et al., 2024), and support GQA by mapping several query heads to one KV head
in the grid instead of materialising repeated keys.

::: napkinmath
[How big can a tile be?]{.box-title}

On an H100 each SM has 228 KB of shared memory and 256 KB of registers. A forward program with
$\texttt{BLOCK\_M}=\texttt{BLOCK\_N}=128$ and $d_{h}=128$ in bf16 holds a $\mathbf{Q}$ tile (32 KB),
a $\mathbf{K}$ and a $\mathbf{V}$ tile per pipeline stage (64 KB for two stages: 128 KB), the fp32
accumulator ($128\times128\times4=64$ KB, in registers) and the fp32 score tile (another 64 KB in
registers). That is close to the limits, which is why $d_{h}=128$ kernels often use
$\texttt{BLOCK\_N}=64$ and why $d_{h}=256$ needs smaller tiles still.
:::

## A playbook for a fast training step {#sec:perf:playbook}

Everything above combines into a checklist, applied in roughly this order and measured after every
step. Start with a baseline profile; keep the list of changes and their measured effect in your log.

1.  **Fit first.** Do the memory budget ([@sec:perf:memory]). If it does not fit, the order
    of remedies is: bf16 activations, FlashAttention, fused loss, selective checkpointing, full
    checkpointing, sharding the optimizer state and parameters across devices
    ([@ch:sharding]), offloading.

2.  **bf16 everywhere it is safe**, with fp32 master weights and fp32 reductions
    ([@sec:perf:amp]); enable TF32 for anything left in fp32.

3.  **Replace attention** with SDPA or your FlashAttention-2 kernel.

4.  **Never materialise the logits.** Compute the LM head and cross-entropy in chunks of tokens, so
    only a $(\text{chunk}, V)$ slab exists at a time, and recompute it in backward (or write a fused
    Triton kernel that computes the loss and the gradient of the logits in one pass; Hsu et
    al. (2024) describe such kernels).

5.  **Fuse the elementwise tail**: `torch.compile` per block; `fused=True` AdamW.

6.  **Shape hygiene**: multiples of 64/128 for every GEMM dimension; pad the vocabulary.

7.  **Remove host synchronisations** from the step (no `.item()` every step, no data-dependent
    Python branches); log asynchronously.

8.  **Kill launch overhead** with CUDA graphs once shapes are static.

9.  **Tune** kernel tile sizes and compile modes last, when the profile shows that the remaining
    time is in a few kernels.

``` {#lst:perf:chunkce .python caption="Chunked LM head plus cross-entropy: peak logits memory is one chunk."}
def chunked_lm_loss(hidden, weight, targets, chunk=4096):
    """hidden (N, d), weight (V, d), targets (N,) -> mean cross-entropy."""
    total = hidden.new_zeros((), dtype=torch.float32)
    for s in range(0, hidden.shape[0], chunk):
        h, t = hidden[s:s + chunk], targets[s:s + chunk]
        def piece(h, t=t):                       # recomputed in backward
            logits = (h @ weight.T).float()      # (chunk, V) only
            return F.cross_entropy(logits, t, reduction="sum")
        total = total + checkpoint(piece, h, use_reentrant=False)
    return total / hidden.shape[0]
```

::: systemslens
[Know when to stop]{.box-title}

Each item on the list has a ceiling you can compute. If the GEMMs already run at 70% of peak, the
best a GEMM-tuning effort can buy is the remaining 30% of GEMM time. If 15% of the step is
optimizer, fusing it buys at most 15%. Rank optimisations by *(time in the targeted kernels)
$\times$ (achievable speedup)*, not by how interesting they are. MFU
([@sec:pretrain:efficiency]) is the scoreboard: a dense model at 50--60% MFU on one GPU has
little single-device headroom left, and the next gains come from scaling out efficiently
([@ch:distributed; @ch:sharding]).
:::

## Summary {#sec:perf:summary}

- Make experiments cheap and recorded: pinned environment, benchmark scripts with flags, sweeps that
  log failures, tables generated by code.

- Time GPU work only after synchronising, exclude warm-up, report spread; use CUDA events or
  `do_bench` for kernels.

- Nsight Systems with NVTX ranges shows where time goes; GEMMs dominate FLOPs, but memory-bound
  kernels often take a large share of the time.

- Mixed precision is a per-op policy; accumulate in fp32 even when storing in 16 bits; measure
  memory rather than assuming autocast saves it.

- Saved-tensor hooks reveal residuals exactly; fusion (`torch.compile`, fused kernels) shrinks them;
  checkpointing trades one extra forward for memory, with the optimal grouping set by the ratio of a
  block's residuals to its input ([@eq:perf:ckpt]).

- FlashAttention-2 stores $\mathbf{O}$ and the log-sum-exp, recomputes $\mathbf{P}$ in a two-kernel
  backward without atomics, and skips the upper triangle of causal attention.

\subsection*{Chapter 3: Text Data, Tokenization, and the Input Pipeline}

\paragraph{Exercise 3.1.} A window starting at offset $s_0$ needs tokens $s_0,\dots,s_0+T$, so valid
starts are $0,s,2s,\dots\le N-T-1$, giving $n=\lfloor (N-T-1)/s\rfloor+1$ windows (for $N>T$). Input
positions per epoch: $nT\approx NT/s$. A typical (interior) token is therefore an input about $T/s$
times: $T$ times for $s=1$, 4 times for $s=T/4$, once for $s=T$.

\paragraph{Exercise 3.2.} (i) \code{"a  b"} (two spaces): decoding re-joins with one space.
(ii) \code{'say "hi"'}: tokens \code{say}, \code{"}, \code{hi}, \code{"} decode to \code{'say " hi"'}
because the regex only removes spaces \emph{before} punctuation, leaving the space after the opening
quote. (iii) any string with a tab or newline: whitespace is discarded and replaced by single
spaces. Byte-level BPE never discards bytes: every byte belongs to exactly one token and decoding
concatenates the tokens' bytes, so \code{decode(encode(s)) == s} for every valid UTF-8 string.

\paragraph{Exercise 3.3.} Random lowercase strings contain few frequent English bigrams, so only
short merges apply: expect roughly 1.5--2.5 bytes per token. A script absent from the training
corpus has no merges at all among its bytes, so each UTF-8 byte is its own token: for a 3-byte
script that is 1 byte/token, i.e.\ three tokens per character. Compression depends entirely on which
byte sequences were frequent in the tokenizer's training data.

\paragraph{Exercise 3.4.} Training learned merges in a specific order and the training corpus was
segmented by applying them in that order; the model only ever saw segmentations produced that way.
Example: merges $[(b,c)\to X,\ (a,b)\to Y]$ and input \code{ababc}. By rank: $(b,c)$ first gives
\code{a b a X}, then $(a,b)$ gives \code{Y a X}. By in-input frequency: $(a,b)$ occurs twice, so it is
merged first, giving \code{Y Y c}, after which nothing applies. Different token sequence, one the
model may never have seen in training.

\paragraph{Exercise 3.5.} Naive: each of $M$ merges recounts all $W$ symbols and scans $P$ pairs:
$O(M(W+P))$. Incremental: initial counting $O(W)$, then merge $m$ costs $O(\sum_{w\in a_m}|w|)$ plus
$O(P)$ to find the maximum, i.e.\ $O(W+\sum_m |a_m|\bar{\ell}+MP)$. A max-heap keyed by count makes the
maximum $O(\log P)$, but counts \emph{decrease} when words are rewritten, and binary heaps do not
support decrease-key cheaply. The standard solution is lazy deletion: push a new $(\text{count},\text{pair})$
entry whenever a count changes, and when popping, discard entries whose count no longer matches the
current table (or use an indexed priority queue).

\paragraph{Exercise 3.6.} With $d=2048$, $L=24$ the non-embedding parameters are about
$12Ld^2\approx1.21$B. (a) Tied embeddings: $32\text{k}\cdot2048=65.5$M vs.\ $256\text{k}\cdot2048=524$M.
(b) Logit FLOPs per token $2\vocab d$: 131\,MFLOP vs.\ 1.05\,GFLOP, compared to $\approx2.4$\,GFLOP for the
rest of the forward pass. (c) $10^{11}$ vs.\ $\approx0.85\times10^{11}$ tokens. (d) fp32 logits for
$B=4$, $T=8192$: $4\cdot8192\cdot\vocab\cdot4$\,B $=4.2$\,GB vs.\ 33.6\,GB. Training compute
$\approx6(N+\vocab d)D$: $7.7\times10^{20}$ vs.\ $9.1\times10^{20}$ FLOPs, so for this size the small
vocabulary is cheaper overall. For a 0.5B model the large vocabulary would be most of the parameter
budget; choose $\approx32$--$64$k. For a 70B model the embedding is a few percent of parameters and
logits a few percent of FLOPs, while 15\% shorter sequences cut attention, KV cache and serving cost:
choose the large vocabulary.

\paragraph{Exercise 3.7.}
\begin{lstlisting}
emb = torch.nn.Embedding(10, 4)
ids = torch.tensor([3, 7, 3])
g = torch.randn(3, 4)
(emb(ids) * g).sum().backward()
nz = emb.weight.grad.abs().sum(1) > 0
assert nz.nonzero().flatten().tolist() == [3, 7]
assert torch.allclose(emb.weight.grad[3], g[0] + g[2])
\end{lstlisting}
With \code{sparse=True} the gradient is a sparse COO tensor holding only the touched rows; it is
accepted by \code{optim.SGD}, \code{optim.SparseAdam} and \code{optim.Adagrad}, but not by \code{Adam}/\code{AdamW}.

\paragraph{Exercise 3.8.} With \code{sa = SelfAttention(d, d)} (no positions), a permutation
matrix $\Pi$ gives $\mathrm{sa}(\Pi X)=\Pi\,\mathrm{sa}(X)$, because $\Pi X W$ permutes rows of $Q,K,V$,
the score matrix becomes $\Pi S\Pi^\top$, the row softmax commutes with that, and
$\Pi A\Pi^\top\Pi V=\Pi AV$. Test: \code{perm = torch.randperm(T); assert torch.allclose(sa(x[perm]), sa(x)[perm])}.
After adding \code{pos\_emb(arange(T))} to the input the property fails, since position vectors are not
permuted with the tokens.

\paragraph{Exercise 3.9.} For frequency $\omega$, $\sin\omega(p+k)=\sin\omega p\cos\omega k+\cos\omega p\sin\omega k$ and
$\cos\omega(p+k)=\cos\omega p\cos\omega k-\sin\omega p\sin\omega k$. Hence each $(\sin,\cos)$ pair is mapped by the
$2\times2$ block $\begin{psmallmatrix}\cos\omega k&\sin\omega k\\-\sin\omega k&\cos\omega k\end{psmallmatrix}$, and $\mat{M}_k$ is block
diagonal with these blocks, independent of $p$. A linear layer can therefore implement ``look $k$
positions back'' uniformly for all positions.

\paragraph{Exercise 3.10.}
\begin{lstlisting}
def doc_causal_mask(ids, eot_id):
    T = len(ids)
    ends = torch.as_tensor(ids) == eot_id
    doc = torch.cumsum(ends.long(), 0) - ends.long()  # EOT belongs to its doc
    same = doc[:, None] == doc[None, :]
    return same & torch.tril(torch.ones(T, T, dtype=torch.bool))  # True = allowed
\end{lstlisting}
The plain causal mask allows $\approx T^2/2$ scores; four equal documents allow
$4\cdot(T/4)^2/2=T^2/8$, so three quarters of the causal scores are skipped.

\paragraph{Exercise 3.11.} With a warm page cache, reads are limited by Python per-item overhead
(tens of thousands of windows per second, as in the chapter's measurement). After dropping caches,
each random window is one small random read: on an NVMe SSD (hundreds of thousands of IOPS at high
queue depth, far fewer at queue depth 1 from a single Python thread) expect thousands to tens of
thousands of windows/s; on a hard disk, about 100/s. Multiple loader workers raise the effective
queue depth and recover throughput.
